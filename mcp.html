Getting started

Connect in under a minute

The server speaks standard MCP over streamable HTTP with no authentication, so any MCP host can connect with just the URL.

  1. Claude: Settings → Connectors → Add custom connector → paste https://mcp.ainumbers.co/mcp. No OAuth prompt; it connects immediately.
  2. ChatGPT (developer mode): Settings → Connectors → Create → server URL https://mcp.ainumbers.co/mcp, no authentication.
  3. Any other MCP client: point a streamable-http transport at the endpoint. The server is also published in the official MCP registry as co.ainumbers/tools.

Then just ask: "compare BaaS providers for a mid-size programme", "score my MCP server's ship-readiness", or "validate this A2A agent card". In hosts that support MCP Apps, results render as interactive widgets you can adjust without re-prompting.

OpenChainGraph v0.4

Compute Binding: verifiable artifacts

As of June 2026, MCP tools that map to an OpenChainGraph kernel run on the server and return a fully verifiable artifact instead of a plain text result. Every artifact carries an execution_hash: a SHA-256 over sorted-key JSON of policy_parameters + output_payload, computed on the server and independently reproducible by any client using the public canonicalization algorithm.

This means you can verify, in your browser, that the result you received from the MCP server is byte-for-byte identical to what the kernel produced for those exact inputs, without trusting any intermediary. The hash algorithm is the same one used by all OpenChainGraph browser tools, so server-side and client-side artifacts are cryptographically interoperable.

🔗
Verify any artifact

Paste any OpenChainGraph artifact JSON into chaingraph/verify.html: the page recomputes the SHA-256 client-side and reports PASS or MISMATCH. The public conformance suite at chaingraph/conformance/run.mjs provides three pinned reference test vectors for art-01, art-09, and art-34. Integration guide: chaingraph/ocg-integration-guide.html.

📋
Inspect composite artifacts in the Agent Work Ledger

Gated workflows return a composite_artifact that includes a decisions[] array recording which gate fired, the observed value, and the branch taken. Drop or paste any artifact into the Agent Work Ledger to replay every gate in your browser, walk the decision path, and verify the execution hash without trusting any intermediary. The ledger_url field returned by run_chain links directly to the pre-loaded record.

Behavior & privacy

How the server treats your data

🔒
No stored inputs, by design
The server collects no accounts, no keys, and no personal data in requests. Deterministic OpenChainGraph compute node. By default (compute:"auto") inputs are computed server-side on Cloudflare Workers for gpu:false nodes with a registered kernel; compute:"browser" forces client-side execution and returns a browser delegation URL instead. gpu:true nodes always delegate to the browser. Inputs are processed transiently to compute the response and are not stored, logged, or retained. Use synthetic or anonymised inputs only. Exports an AP2 artifact with execution_hash for chain provenance. There is no database, and nothing is shared with or sold to third parties. Each call does write a lightweight telemetry record for abuse and rate-pattern monitoring: tool name, a coarse caller identifier, success/failure, latency, and chain depth, never inputs, parameters, or outputs. The caller identifier is a hash of your IP address with a fixed public pepper; because the pepper is public and IPv4 addresses are a small, enumerable space, treat it as pseudonymous, not anonymous. Separately, once per connection (at MCP initialize, not on every call), the server also records your MCP client's declared name and version, your User-Agent header, and the network ASN your request arrived from. These are network- and software-level identifiers, not per-user identifiers on their own: many callers share the same ASN and the same client version. But on a small ASN paired with an uncommon client version, the combination can narrow to a specific organization or workstation, so it gets the same treatment as the caller hash above: pseudonymous, not anonymous. Neither record stores your raw IP address or any per-user identifier. Privacy questions: see Support below.
🧩
Widgets run client-side
The 15 widget tools return self-contained interactive panels (MCP Apps). Once rendered in your chat, all interaction (sliders, re-weighting, re-validation) runs locally in the widget. Deterministic: same inputs, same outputs.
👁️
Read-only, annotated
All 17 tools declare readOnlyHint: true. Nothing on the server or in your environment is modified by any call: the server computes, renders, and returns.
⚡
Fast and globally served
Runs on edge infrastructure with no cold starts. Health check: mcp.ainumbers.co/healthz. Source is open: the server repo is on GitHub.
🔗
Prefill deep-links

Catalog results from list_ainumbers_tools include deep-links of the form tools/{slug}.html#in=<base64url JSON>[&run=1]. Your values travel in the URL hash fragment (they are never transmitted to a server) and the destination tool fills (and optionally runs) entirely in your browser.

Run it inside your own perimeter

Deploy your own org instance

The public server at mcp.ainumbers.co/mcp is free, unauthenticated, and open to anyone. If your organization would rather keep MCP traffic inside its own Cloudflare account, network egress rules, and audit logs, fork the server repo and run it yourself. The fork is free; nothing about self-hosting is gated or metered.

The ainumbers-mcp-apps repo boots straight from the tool data and kernels already committed to it – no build step required at deploy time. Fork it, click Deploy to Cloudflare on the README, and wrangler stands up the Worker on your account:

Two lines in wrangler.jsonc need to change before that first deploy succeeds on a fresh account, and the README spells out exactly why:

  • Worker name and routes: the committed config points routes at mcp.ainumbers.co, a zone the fork owner does not control. Rename the worker and either delete the routes block (ship on the free workers.dev subdomain) or point it at a zone already in your own Cloudflare account.
  • Queues and Workflows are optional: the event queue and the renewal-watch Workflow feed an internal analytics loop and are both guarded in code (if (env.EVENTS_QUEUE) / if (env.RENEWAL_WATCH_WORKFLOW)), so the MCP handshake and every tool call work with them absent. Queues require a Workers Paid plan; drop the queues and workflows blocks entirely to stay on the free tier.

Everything else in the config, including the ASSETS binding that serves the committed tool data, works unmodified on a fresh account.

The public server fronts /mcp with a Cloudflare WAF rule: 50 requests per 10 seconds per IP, action Block. Copy that recipe onto your zone (Security → WAF → Rate limiting rules) once your fork is live; it is the same rule this estate runs on itself.

The upstream repo vendors new tool kernels and MCP fixes on an ongoing basis. Watch the repo's Releases feed and pull upstream on a cadence that fits your change-control process; nothing about the fork auto-updates for you.

Your internal server still anchors to external, public timestamp authorities for its execution proofs – that is the point. Running the MCP endpoint inside your perimeter does not change where the cryptographic anchor lives, so the receipts your fork issues stay verifiable against the same public record as ours.

If Helm is part of your stack, point its org config at your internal endpoint instead of the public one (?config= on the Helm app) so every workstation in the org resolves to your fork automatically.

🛡️
Check your deployment for conformance

A self-hosted fork can run the same SPEC.md §15 and §26 gate suites that validate the public server against your own endpoint, and self-assert the result. See the conformance badge program for scope and criteria.
