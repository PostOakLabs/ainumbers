Run five tools in sequence to stand up an agentic checkout: validate the merchant or wallet A2A agent card and its declared payment extensions, build the Google AP2 checkout and payment mandates (verifiable digital credentials), simulate settlement over the x402 payment-required flow, verify the RFC 9421 request signatures that Visa's Trusted Agent Protocol relies on, and finish with a protocol-by-protocol field crosswalk to lock your stack — the complete pre-launch validation chain for agent-initiated payments.

A2A v1.0 Discovery

A2A Agent Card Validator & Extension Checker

Agentic checkout starts with discovery: the buyer's agent has to find and trust the counterparty agent before any money moves. The A2A agent card is that trust anchor — a JSON document declaring the agent's identity, capabilities, transport endpoints, signing keys, and payment-protocol extensions (AP2, x402). This validator checks your agent card against the A2A v1.0 shape, verifies signed-card signature structure, and confirms which payment extensions the card actually declares — because a checkout chain built against an extension the card never advertised fails at the first handshake.

↳ Inputs
Agent card JSON (yours or the counterparty's), declared transport endpoints, signing key references, AP2 / x402 extension blocks.
→ Outputs to Step 2
Validated agent card, shape and signature findings, and the confirmed list of declared payment extensions — this determines which mandate format Step 2 builds.

Google AP2 VDC Mandate

Google AP2 Checkout/Payment Mandate (VDC) Builder & Validator

With discovery confirmed, the agent needs authority to transact. In Google's Agent Payments Protocol (AP2), that authority is a mandate — a verifiable digital credential capturing what the user authorised: the checkout contents and the payment terms. This builder constructs both mandate types against the current AP2 structure (including the legacy Intent/Cart to Checkout/Payment mapping), validates field presence and consistency, and flags fields whose exact published schema is still evolving as illustrative. The result is the authorisation artifact the settlement leg in Step 3 executes against.

↳ Inputs from Step 1
Declared AP2 extension support from the validated agent card, checkout contents (items, amounts, currency), payment method constraints, user-presence mode, expiry windows.
→ Outputs to Step 3
Structured AP2 checkout + payment mandate JSON with validation findings — the authorised amount, currency, and constraints carry into the x402 settlement simulation in Step 3.

x402 402 Flow

x402 Header Decoder, Payload Linter & 402 Flow Simulator

Authorisation in hand, money has to move. x402 revives HTTP 402 Payment Required as a machine-native settlement leg: the resource server answers 402 with payment requirements, the agent constructs an X-PAYMENT header carrying the signed payment payload, and a facilitator verifies and settles. This tool decodes and lints X-PAYMENT headers field by field, validates the payment-requirements structure, and simulates the full request → 402 → retry-with-payment → settle sequence so you can see exactly where a malformed payload, an amount mismatch against the Step 2 mandate, or a missing scheme entry breaks the flow.

↳ Inputs from Step 2
Authorised amount, currency, and constraints from the AP2 mandate; X-PAYMENT header samples; payment-requirements JSON from the resource server; selected scheme/network pair.
→ Outputs to Step 4
Decoded header findings, payload lint results, and a step-by-step 402 flow trace — the signed request leaving this flow is what Step 4 verifies cryptographically.

Visa TAP RFC 9421

Visa Trusted Agent Protocol Signature Inspector & Readiness

Card networks need to distinguish a trusted agent's traffic from bot traffic — Visa's Trusted Agent Protocol does this by requiring agents to sign requests with HTTP Message Signatures (RFC 9421). This inspector parses Signature-Input and Signature headers, checks covered components, key identifiers, and expiry windows, lints the agent's JWKS (including the private-key-leak self-check), and scores overall TAP readiness. Every payment request your agent emitted in Step 3 should survive this verification — if it doesn't, the merchant's gateway will treat your agent as an untrusted bot.

↳ Inputs from Step 3
Signed request samples from the x402 flow (Signature-Input / Signature headers), the agent's JWKS, covered-component list, key rotation and expiry policy.
→ Outputs to Step 5
Signature verification findings, JWKS lint results, TAP readiness score — surviving signature discipline is a stack-selection criterion carried into Step 5.

5 Protocols Field Crosswalk

Agentic Payments Protocol Comparator & Field Crosswalk

You've now touched three protocol families in one checkout — A2A for discovery, AP2 for mandates, x402 for settlement, TAP for trust. The final step is the architecture decision: which combination ships to production? This comparator puts AP2, ACP, x402, Visa TAP, and Mastercard Agent Pay side by side — authorisation model, settlement leg, signature scheme, mandate semantics — and generates a field-level crosswalk so you can see exactly which fields map, which translate lossily, and which have no counterpart. The output is a routing-policy-shaped stack recommendation you can defend in an architecture review.

↳ Inputs from Steps 1–4
Declared extensions (Step 1), mandate structure (Step 2), settlement constraints (Step 3), signature readiness (Step 4), plus your merchant category and corridor requirements.
→ Final Output
Protocol comparison matrix, field-level crosswalk table, and a stack recommendation with gap list — the launch-ready architecture decision record for your agentic checkout.
