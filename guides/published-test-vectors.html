Published test vectors

Written for engineers implementing agent payment flows who want to check their code against fixed, recorded values. The AINumbers kernels publish golden test vectors as JSON fixtures in the public repository: each vector records the inputs a node accepts, the exact output a recorded run produced, and a hash over both. Take the inputs, run them through your own implementation, compare the output, recompute the hash. This page explains what the vectors are, lists the nodes that publish them, and walks through the comparison step by step. For the replay workflow against exported Policy Mandates, see the mandate regression replayer.

What a test vector is

A test vector is one recorded case: a fixed input and the exact output the kernel returned for it. The vectors live as fixture files in the public repository under chaingraph/kernels/fixtures/, one file per node: chaingraph/kernels/fixtures/. Each file holds a vectors array, and every vector carries five fields:

name, a stable identifier for the case; note, a short provenance comment; policy_parameters, the exact caller-supplied inputs the node accepts; output_payload, the exact output the recorded run produced; and golden_hash, a SHA-256 digest over both of those objects.

The digest comes from chaingraph/kernels/_hash.mjs, the single canonicalization the project uses for every execution hash: RFC 8785 (JSON Canonicalization Scheme) over the object {policy_parameters, output_payload}, hashed with SHA-256 and rendered as lowercase hex. There is exactly one canonicalization. Two implementations that produce the same output but canonicalize differently will produce different hashes, so the hash is also a check on canonicalization.

How to compare your implementation

  1. Pick a vector from a fixture file and take its policy_parameters object verbatim, with every field and value exactly as recorded.
  2. Run your implementation on those inputs, the way your code performs the equivalent operation.
  3. Compare your output to the vector's output_payload field by field: field names, value types, and value formats all count. A field-by-field comparison is stricter than a parsed-equality check and is the one that detects representation drift.
  4. Recompute the hash. Canonicalize {policy_parameters, output_payload} with the RFC 8785 rule that chaingraph/kernels/_hash.mjs implements, hash the canonical bytes with SHA-256, and compare to golden_hash. If your output matched and your hash differs, your canonicalization differs. The simplest way to rule that out is to import _hash.mjs rather than reimplement the canonicalization.

Step 4 is deliberately narrow: the hash covers exactly the two recorded objects and nothing else, so a match on both steps pins your implementation's output and your canonicalization at the same time.

What a match means

A match is a reproducibility result. It means your implementation, given the vector's policy_parameters, returned output equal to the recorded output_payload field for field, and that a hash computed the project's way over those two objects equals golden_hash. A match also tells you your canonicalization agrees with _hash.mjs.

A match carries no conformance claim about any standard, protocol draft, or regulation, and it says nothing about behaviour on inputs the vectors do not cover. The vectors cover the cases they cover: their number and subject are in the table above. Publication of the vectors expresses no opinion about any implementation, and no relationship between any implementation and this site follows from a match.

Reporting a mismatch

If your output differs from output_payload on inputs you copied verbatim, or your recomputed hash differs from golden_hash while your output matches, check your canonicalization against _hash.mjs first. If the recorded values themselves look wrong, open an issue on the repository's public issue tracker with the vector name and fixture file, your output, and your computed hash. A suspected error in a recorded vector is handled like any other repository defect: it gets checked against the kernel and fixed in the fixtures if it is wrong.
