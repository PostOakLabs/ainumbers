Registry Schema Skeleton Gen

MCP server.json Validator & Registry-Ready Skeleton Generator

Everything downstream — registry listing, client discovery, namespace trust — keys off server.json, and the official MCP registry rejects malformed descriptors outright. This validator checks your server.json against the registry schema: reverse-DNS name format and namespace-to-auth-method match (io.github.* for GitHub auth, com.example.* for domain auth), version semantics, remotes vs packages structure, transport types, and template-variable syntax. No server.json yet? The skeleton generator produces a registry-ready starting point from a handful of answers.

↳ Inputs
Your draft server.json (or answers for the skeleton generator), intended namespace and auth method, remote endpoint URL or package identifiers, transport type.
→ Outputs to Step 2
Schema-valid server.json with finding list, confirmed namespace/auth pairing — the declared tool surface is what Step 2 lints definition by definition.

Tool Lint Annotations

MCP Tool-Definition Linter & Annotation Designer

Missing safety annotations are among the most common reasons connector reviews fail — every tool should truthfully declare readOnlyHint, destructiveHint, idempotentHint, and openWorldHint so clients can gate confirmation prompts correctly. This linter checks each tool definition for name conventions (verb_noun), description quality, inputSchema completeness and type discipline, oversized result risk, and the full annotation set — and the annotation designer walks you through choosing hints that match what the tool actually does, not what makes review easier.

↳ Inputs from Step 1
The tool definitions declared by your validated server (names, descriptions, inputSchemas, annotations), expected result sizes, side-effect inventory per tool.
→ Outputs to Step 3
Lint findings per tool, designed annotation set, corrected definitions — the declared side-effect surface determines how strict the Step 3 authorization audit must be.

OAuth 2.1 RFC 9728 / 8707

MCP OAuth 2.1 Authorization Auditor

If your server requires auth, the authorization chain is where most remote MCP deployments quietly go wrong. This auditor validates the RFC 9728 protected-resource metadata document, checks the discovery chain from 401 challenge to authorization-server metadata, verifies RFC 8707 resource-indicator (audience) binding so tokens minted for your server can't be replayed elsewhere, and runs the token-passthrough and confused-deputy self-checks. Serving a public no-auth tool set? Run it anyway — it confirms you aren't accidentally advertising auth metadata that clients will trip over.

↳ Inputs from Step 2
Side-effect surface from the linted definitions, protected-resource metadata JSON, authorization-server metadata, 401 challenge headers, token audience samples (synthetic).
→ Outputs to Step 4
Authorization audit findings — discovery-chain validity, audience binding, passthrough and confused-deputy verdicts — auth posture feeds the Step 5 composite score.

OWASP ASI01 Injection Scan

MCP Tool-Poisoning & Prompt-Injection Manifest Scanner

Tool descriptions are executed as model context — which makes them an injection surface. A poisoned description can instruct the model to exfiltrate data, shadow another server's tools, or silently change behaviour, and hidden-unicode tricks make the payload invisible to human review. This scanner runs heuristic detection across your manifest: hidden/zero-width unicode, imperative instructions aimed at the model rather than the user, exfiltration-shaped URLs and parameters, tool-shadowing name collisions, and description/behaviour mismatches — the OWASP ASI01-class checks a serious directory review applies to your listing.

↳ Inputs from Step 2
The full tool manifest with corrected definitions from Step 2 — names, descriptions, schemas, annotation claims — plus any third-party tool descriptions you re-expose.
→ Outputs to Step 5
Poisoning scan report — flagged patterns by severity, hidden-unicode findings, shadowing collisions, clean-pass confirmation — security posture feeds the Step 5 composite score.

Composite Launch Verdict

MCP Developer Readiness Scorecard

The flagship composite: this scorecard rolls the whole chain into one graded verdict — server.json validity, tool-definition and annotation quality, authorization posture, injection-scan results, plus transport hardening and spec-revision currency. Each dimension gets a sub-score with a direct link to the tool that fixes it, so the output doubles as your remediation worklist. Walk into a registry publish or a connectors-directory submission with a green scorecard and the review has nothing left to find.

↳ Inputs from Steps 1–4
server.json findings (Step 1), lint and annotation results (Step 2), authorization audit verdicts (Step 3), poisoning scan report (Step 4), transport and spec-revision answers.
→ Final Output
Composite readiness grade with per-dimension sub-scores, gap list linked to the fixing tool, and a submission-ready summary — your pre-publish decision record.
