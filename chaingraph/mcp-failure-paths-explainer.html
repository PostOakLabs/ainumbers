What the MCP worker does when a call goes wrong

An agent calls a tool. The call can arrive broken, run long, or hit a limit. This page walks one tools/call through the failure paths of the AINumbers MCP worker and shows that each one ends safely: the agent can retry, and every error tells it what to do next. The happy path, where the call simply works, is covered step by step on How MCP runs one workflow. Every value shown was captured from the live worker endpoint on 2 November 2026, with the calling command quoted in this page's sources.

Presenter mode shows one step per screen. Arrow keys move, A toggles autoplay, Esc exits.
Goal of this animation

Show that the MCP worker keeps no state between calls, yet an agent can retry safely and every failure tells it what to do next. One tool call, three things that can go wrong, each ending safely.

1
Step 1

Cold start: the worker forgets everything between calls

A new worker isolate starts with an empty search index and builds it lazily, only when a search actually needs it. Nothing about your conversation, or the previous call, survives.

The worker is serverless in the plain sense: it runs on Cloudflare Workers, which scales to zero and starts fresh isolates on demand. That is why cold start is a normal condition here, not an error. The served tool catalogue is 763 tools; an initialize handshake answers with the server name, protocol version and capabilities before any of them runs.

2
Step 2

Bad input: the schema catches it before any kernel runs

Every served tool carries its input contract as a JSON Schema in the 2020-12 dialect. A malformed field is rejected at the door with a code that says fix the input, and an unknown key comes back as a warning instead of being silently dropped.

Two different refusals live at this door and they never share a code. A wrong value or shape is invalid params, code -32602, and the remedy is to fix the input. A request that is too frequent is rate limiting, code -32029, and the remedy is to wait: its registry entry carries retryable true, the one protocol cause that says retry. Unknown keys in an otherwise valid call are not dropped quietly; the worker warns about them so a typo in a tool name or field cannot silently change what runs.

3
Step 3

Error shape: a stable code and a retryable flag on every failure

Every tool error carries a stable JSON-RPC code and a retryable flag, so an agent can decide mechanically whether to resend, wait, or give up. This error object below was produced by the live worker on 2 November 2026 by sending a number where the tool expects a text tenor.

The worker keeps an internal error registry where each cause owns one code forever. Three examples measured in the worker's published source: rate limit is -32029 with retryable true, because the remedy is time. Server timeout is -32001 with retryable true, because the same call may succeed later. Invalid params is -32602 with retryable false, because resending the same broken input would fail the same way. The text content of an error is byte identical to what earlier clients saw, so a code you learned still means the same thing.

4
Step 4

Timeout and retry: the same inputs seal the same answer

When a call times out, the agent resends the exact same inputs. Because every kernel is a pure function, the result carries the same execution_hash, and the retry returns the identical sealed answer instead of triggering a second action.

The hash is SHA-256 over RFC 8785 canonical JSON of the policy parameters and the output payload, so it depends on the meaning of the call and not on the moment it ran. The two captures quoted here ran one second apart and produced different generated_at timestamps and the same 64 character hash. What a retry must never do is act twice: the guarantee that one answered call means one purchase is held on the shopping agent page, One agent makes one purchase through three workflows, and this page does not re explain it.

5
Step 5

WebMCP runs the same kernel offline

WebMCP direct execution runs the same kernel inside a virtual machine gate in the page and produces the same execution_hash. The worker and the browser are two doors to one function.

The browser door is explained fully on How WebMCP runs one workflow. The point this page adds: because both doors execute the same kernel code, a hash sealed in the worker verifies against a hash computed offline in a tab. Privacy works the same in both: no AINumbers server stores your inputs, and the AI host you call through is yours to choose.
