Solana DvP Pre-Funding Terms Verifier

The Solana Foundation DvP program's README requires funders to verify a SwapDvp record before depositing, because CreateDvp is permissionless and a forged record can name attacker destinations. Paste the record you read on-chain, the mint descriptors, the cluster time, and the agreed deal this verifier recomputes the checklist: pinned program owner, exactly 458 bytes, terms match, expiry windows, blocked Token-2022 extensions, and the 32-per-leg hook cap, plus the trusted-authority risks the program accepts as-is. Values only , no RPC, no keys, no on-chain writes. The output is a recompute, not legal finality and not proof of agreement.

How the checks map to the pinned clauses

Owner , README Notes line 33 + the lib.rs declare_id pin: the account must be owned by dvp34bdbcEm4f4FCUjGV4mDAkDshaQR4LkK8fdcsyZq.

Length , the struct pin: SwapDvp::LEN = 1 + 32×7 + 8×4 + 64 + 32×2 + 32×2 + 1 + 8 = 458. A look-alike account of any other length is not a SwapDvp.

Terms , README Notes line 33: amount_a/amount_b, expiry, earliest, user_a, user_b, settlement_authority and both settlement destinations must equal the agreed deal.

Windows , README Notes lines 24/26/27: only Settle rejects after expiry (so expiry must be in the future at your supplied cluster time); earliest must be ≤ expiry; expiry is capped at one year past creation (fixed 365-day year). Budget ~60s of cluster-clock drift.

Blocked extensions , the token_utils pin: TransferFeeConfig, InterestBearingConfig, ScaledUiAmountConfig, NonTransferable each fail with BlockedMintExtension. The recovery paths tolerate them; funding does not.

Hook cap , README Notes line 35 + MAX_HOOK_REMAINING_ACCOUNTS: hook extras are capped at 32 accounts per leg. A mutable hook can raise its list after funding, which is a trusted-authority risk, not a rejection.

Trust flags , README Notes lines 34-35: PermanentDelegate, Pausable, MintCloseAuthority, TransferHook, ConfidentialTransfer and DefaultAccountState / freeze authority are accepted as-is by the program; the verifier surfaces them and never turns them into failures.

Scope and provenance

This verifier recomputes a checklist over pasted values; per README Notes line 31, a record is not proof of agreement, so the output carries no legal finality. Address derivation, escrow balances and recipient-ATA ownership stay with the on-chain checked helpers, the Cantina audit's scope mapping for this commit is unverified and stays out of scope here, and every constant comes from the pinned DvP clause snapshots (per-branch dispositions live in the branch inventory, including the two declared unrepresented branches on PDA seeds and recipient-ATA ownership).
