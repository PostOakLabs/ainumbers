What our Dafny proofs found

When a proof run restates a kernel over exact numbers and checks it, the kernel, the spec, our test harness and our own scoring tools all get compared against each other. Any disagreement means one of them is wrong. This page sorts what the remediation turned up by where the error actually lived, with real examples from the estate.

Part one · The idea

Why a proof run finds things

The companion page How a Dafny proof checks a kernel explains the four gates. This page is about what happens when something does not line up.

1
Step 1 · The detector

Every proof run compares four independent things

A run holds the shipped kernel, a spec written in plain sentences, a test harness that checks the kernel on tens of thousands of random inputs, and the Dafny model the solver checks. Each was produced separately. When two of them disagree, the run stops and someone has to find out which one is wrong.

The harness runs first, on 20,000 to 25,000 random and adversarial inputs per kernel, before any proof is attempted. That ordering is deliberate: it is far cheaper to catch a wrong sentence with a random input than with a failed proof.

Part two · Where the errors lived

Six kinds of finding

Each step names real kernels. Kernel numbers link to their public node pages.

2
Step 2 · The kernel

Some findings were real defects in shipped kernels

These are the findings the whole effort exists for. In each case the kernel did something on a legal input that no fixture had exercised, and the proof run could only proceed by excluding that input and saying so.

KernelWhat the proof run foundState
art-259 multilateral nettingA zero or missing FX rate divides by zero, and the settlement loop then never finishes.open
art-282 claiming optimizerAt a discount rate of exactly −100 percent the discount factor becomes zero and the present value stops being a finite number.outside proof
art-172 and art-63A null input throws a raw type error where a structured refusal belongs.outside proof
art-255 LCM rate derivationTwo values are computed and then never returned, so no property can be stated about them.noted

A proof never quietly absorbs a defect like these. The model's stated domain excludes the bad input, the record says so in plain words, and the kernel needs its own fix before the exclusion can go. The netting defect is still open on 27 November 2026.

3
Step 3 · The spec

Some properties were false as first written

A spec sentence is a claim about every input. Drafted from the kernel's description, a sentence can sound right and still fail on an edge nobody pictured. The harness or the solver finds the counterexample, and the sentence is rewritten to what is actually true. The kernel does not change.

KernelDrafted sentenceWhat was true
art-254Headroom is never negative.Only when capital itself is not negative.
art-179A confidence level of exactly 100 falls on one side of the ladder.It falls on the other side; the polarity was reversed.
art-154The lag always rounds to the exact value.Half-cent ties round differently in the shipped code, so the sentence became conditional.
art-541The average uses raw improvements.It averages already-rounded values while the flag uses the raw sign.

Catching these is the point of stating properties before proving them. Each false draft would have become a public claim that the kernel does something it does not. None of them reached a proof record.

4
Step 4 · The harness

Our test harness was often the thing that was wrong

The harness is an executable reading of the spec, written for each kernel and run on thousands of random inputs. When it disagrees with the kernel, the first suspect is the harness. In many runs the kernel was right all along and the harness had guessed an input shape or a default wrongly.

KernelWrong harness assumption
art-166Coordinates arrive as pairs. They arrive as flat points.
art-272The default tranche is 100. The kernel's default is 0.
art-223Three guesses about the shape of a refusal, all wrong. The kernel was correct.
art-259A null FX rate means a missing default. The kernel reads it as zero.

This was the most common finding, and it is healthy. A harness that agrees with the kernel on the first try has usually been written by reading the kernel, which makes the comparison worthless.

5
Step 5 · Floating point

Rounding gaps are measured and kept in the record

The model works over exact numbers while the shipped kernel uses binary floating point. On a value that sits exactly on a half cent, the two can round in different directions. These gaps are real behaviour of the shipped code, so they are counted and published as divergences. No property is weakened to hide one.

The harness for art-265 logged 44 such ties and the one for art-248 logged 87, plus one input large enough to overflow. art-154 returned 33.99 where the exact value was 34.00. Each proof record states the largest divergence measured on its golden vectors next to the proof claim.

6
Step 6 · The scorer

Automated proof runs found every loophole in our scorer

The mutation gate scores how much a spec notices small edits. Automated runs aimed at that score, and in doing so they exposed each place the scorer counted something that did not reflect spec strength. Every loophole was closed with a mechanical rule, and every earlier result was scored again under the new rules.

The first loophole mattered most. A mutant that breaks the file's syntax fails to verify for a trivial reason, so it looked like a kill. Removing those from the count lowered some scores sharply, and it is why kernel 513's record in the companion page lists 38 excluded mutants.

7
Step 7 · Padding

A padded spec is rejected

When a spec scored below the bar, automated runs sometimes added clauses that are true by construction, such as stating that a symmetric function is symmetric. Those clauses are easy to kill and raise the score without saying anything new about the kernel. Under the closed scorer they no longer count.

Re-scoring showed something useful: for most kernels the original unpadded spec already cleared the bar once the scorer stopped counting noise. Four kernels whose score depended on padding were rejected outright and are not retried for now.

8
Step 8 · The prover

Some kernels meet the edge of what the prover can state

Dafny's exact reals have no square root, and our rules forbid adding one as an unproved axiom. Two margin estimators take square roots of holding periods, so their proofs cover only the inputs whose roots are exact. The record names that restriction.

The two kernels are art-50 and art-51, both proved for a single tenor bucket. Smaller gaps were worked around inside the model: rounding up, minimum and maximum are defined locally because Dafny's reals do not provide them, and text parsing, dates and hashing are handled outside the model with the hand-off stated in the record.

Part three · Consequences

What each kind of finding changes

Only one kind of finding changes shipped code. The others change our own drafts and tools, which is where most of the remediation effort went.

9
Step 9 · Outcomes

Each kind of finding has a fixed response

The response depends only on where the error lived. That keeps the outcome mechanical and keeps anyone from talking a finding away.

Where the error livedWhat changesWhat the proof record says
shipped kernelThe kernel needs its own fix. The proof excludes the bad input until that fix lands.The excluded input, in plain words.
spec draftThe sentence is rewritten to what is true, usually as a condition.Only the corrected sentence.
test harnessThe harness is corrected and re-run on fresh random inputs.Nothing; the kernel was right.
floating pointNothing in the kernel or the spec.The largest measured divergence on the golden vectors.
scorerA new mechanical rule, then every past result is scored again.Each excluded mutant group with its count.
padded specThe proof is rejected.No record is written.
prover limitThe proof covers a stated subset of inputs.The restriction, in plain words.

A proof only covers what its spec states, so a kernel with a clean record can still be wrong about what a regulation means. For how the gates work, see How a Dafny proof checks a kernel. For how this tier sits beside our other evidence, see the formal claim tiers and our methods page.
