Proving a tool was never published

A missing web page is not evidence of anything: a 404 can mean a broken link, a moved file or a censored server. This page walks through how the AINumbers registry does better. Over a sorted Merkle tree of every published tool digest, a short cryptographic proof shows that one particular digest sits in no gap, and a public transparency log pins the tree itself so it cannot be quietly swapped later. Every hash on this page is a real value measured from the published registry, and the proof you see was produced and verified by the estate's own code.

Goal of this animation

Show how static files plus a public log can prove a negative: that a claimed AINumbers kernel digest does not exist in the published registry, with each step checkable by anyone.

1
Step 1

A digest with a claim

An agent is handed a kernel digest that claims to be an AINumbers kernel. Asking any single server for it and getting a 404 back proves nothing: the same answer follows from a broken link, a deleted file or a lying server.

The registry does not answer the question with a lookup. It answers it with a data structure that makes the answer checkable, which the next steps build up.

2
Step 2

One tree over every published digest

The registry maintains a Merkle tree whose leaves are every published kernel digest, sorted byte by byte. The root is a single 32-byte value that commits to the whole set and to its order, under the pinned proof specification named ainumbers-simple-v1.

At the 2026-11-02 snapshot the tree covers 687 keys and its root is fb7585a086d5e33dd0b8be2cd3d3e5ac083250401b36a92485905b24b877d002.

3
Step 3

The non-existence proof

To prove the missing digest, the tree produces the two published keys that would bracket it, plus each key’s audit path of interior hashes up to the root. Recomputing both paths must land on the one committed root, and the query must sit strictly between the two neighbours.

For the demo digest a351edd292acf517eb1bbea0adfc22a940a6216a8639e832bf3e81e790c05ac0, the bracketing keys are a255de01b67ae52790e981e245331dbb46ba3aeeec9c86f951688603f24bff64 and a394588aa87698b40dba7cc1d088b210f1a1043ea22387e7b104adb71ab9cb20, with audit paths of 10 hashes each. The landed verifier accepted both paths against the snapshot root. The full proof object is inlined in this page's source.

4
Step 4

A root the lineage log commits to

A tree root quoted in passing could always be a root invented after the fact. So each rebuild of the tree appends a record to an append-only lineage log, binding the root and its key count together. Absence is only ever argued against a root that the log has committed to.

The snapshot’s binding is record 104 of 105. A verifier can walk the log’s own hash chain and check that the root quoted on this page is the log’s committed head, never a hand-picked ancestor.

5
Step 5

The log head is anchored where nobody can rewrite it

The lineage log’s head is published into a public transparency log at every publish, so each record inherits a timestamp and an inclusion proof that exist outside this estate. The anchor for the snapshot here is leaf index 77056 in the Sigsum log, with 13 witnesses cosigning the tree head.

Transparency logs, timestamps and receipts each have their own page; this step only connects them. See the links in the snapshot and sources section below.

6
Step 6

The honest failure states

The proof claims exactly one thing: a named digest is not in a named tree at a named anchor. Everything else that could go wrong is modelled as a distinct failing state, never silently flattened into "absent".

These refusals are the verifier’s own (the generator refuses; these are its own rules): the generator refuses to build a tree from fewer than 2 keys, refuses to construct a non-existence proof for a key that is present, and the publish check treats a missing, stale or unbound tree as failure.
