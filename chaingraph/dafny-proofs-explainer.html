How a Dafny proof checks one of our kernels

Every AINumbers kernel is a small JavaScript function with published fixtures. A Dafny proof restates that function as a model over exact numbers, writes down what it must guarantee, and has a solver check each guarantee for every possible input. This page walks one real proof through the four gates it must pass, then shows how many kernels have reached each stage.

Goal of this animation

Show what a machine-checked proof adds to fixture tests, what each of the four gates catches, and where the estate stands on 27 November 2026.

No server to trustThe proofs run on our own machines with the free Dafny 4.11.0 toolchain and its bundled Z3 4.12.1 solver. Nothing on this page calls a server; every value is a constant in the page source.
Where the numbers come fromThe example record is the proof record for kernel 513. The inventory in step 9 was counted on 2026-11-27 from every proof run's own verdict file, across all of our machines.

Part one · The idea

What a proof adds to a test

The first three steps build the object being checked before any gate runs.

1
Step 1 · Coverage

A test checks points while a proof checks the whole range

A fixture test runs the kernel on a handful of chosen inputs and compares the answers. A proof states a property once and has a solver show that it holds for every input the kernel accepts.

This is the same difference that separates sampling from an exhaustive argument. Fixtures still matter: they are how the proof is tied back to the running code in step 7.

2
Step 2 · The twin

The proof is about a twin of the kernel

Dafny cannot read our JavaScript. Each proof therefore starts from a Dafny model of the same computation written over exact reals and integers, so rounding error cannot hide a mistake in the logic. The properties live on the model as ensures clauses.

The two links in the drawing are different in kind. The green one is a proof. The amber one is a measurement: step 7 replays the published fixtures through a compiled copy of the model and the shipped kernel and records the largest difference. Every proof record states both halves.

3
Step 3 · The spec

Two independent readings of the spec are reconciled

A proof is only as good as the properties it states. To keep the spec from simply echoing the code, it is written twice: once from the kernel source and once from the kernel's published manifest. A mechanical reconcile step keeps what both readings support.

No person writes, signs or approves a clause, a tolerance or a verdict. A human signature would add a name without adding evidence, so every result rests on checks anyone can re-run.

Part two · The four gates

What a proof must pass

A proof counts only when all four gates pass on the same files. The example throughout is kernel 513, the margin call collateral mobilizer.

4
Step 4 · Gate one

The solver discharges every obligation

Dafny turns the model and its clauses into proof obligations and hands each one to the Z3 solver. The gate passes only on the line verified, 0 errors. For kernel 513 that line reads 33 verified, 0 errors, after 1.4 seconds of solver time.

The model may not use assume, {:axiom}, {:verify false} or {:extern}, since each of those lets a proof skip work. A proof that needs one is dropped. The single exception is a declared floating point rounding model, which must be named in the record with its exact clause.

Dafny 4.11.0Z3 4.12.133 verified, 0 errors
5
Step 5 · Gate two

A control shows each lemma has real content

A lemma whose assumptions contradict each other proves anything at all, including false statements. So each lemma gets a control copy with the same assumptions and the conclusion false. The control must fail to verify. If it verifies, the lemma was empty and the gate fails.

For kernel 513 all 20 lemmas were checked this way and every control failed, as it must. A second witness check confirms the golden vectors satisfy the model's preconditions, so the proved properties apply to inputs that actually occur.

6
Step 6 · Gate three

Mutants measure how much the spec notices

A spec can verify and still be too weak to matter. The mutation gate makes small deliberate edits to the computation and its clauses and re-runs the verifier on each one. A good spec makes verification fail, which kills the mutant. At least 80 percent of counted mutants must be killed.

Only mutants inside the scored computation count. Four kinds are excluded: a mutant that no longer compiles, which would otherwise count as an easy kill; a mutant inside a helper method added around the computation; a mutant inside a lemma; and a clause that still verifies when the model's outputs are replaced by arbitrary values, since such a clause says nothing about the computation. Each rule closed a real loophole that automated proof runs found, and every earlier result was re-scored under it.

7
Step 7 · Gate four

Golden vectors replay through both twins

The Dafny model is compiled to JavaScript. Each published golden vector runs through the compiled model and through the shipped kernel, and every output field is compared within a stated tolerance. The largest difference becomes the measured half of the claim.

This gate is what ties the proof to the code people actually run. It is a measurement on the published vectors, which is why the claim says measured rather than proved for the JavaScript.

Part three · The record and the estate

What gets kept and how far it reaches

The last three steps read one proof record, count every proof across the estate, and show how a reader can re-check one.

Step 8 · The receipt

Step 9 · The inventory

169 kernels have a Dafny model today

Step 10 · Re-check

Three commands re-check a proof

Each proof folder holds model.dfy, the reconciled spec.md, the golden fixtures.json and proof-record.json. When a folder is published, re-checking it needs only free tools and no account.

Re-check gate onefree tools only
dotnet tool install --global dafny --version 4.11.0
dafny verify model.dfy
sha256sum model.dfy   # compare with model_digest in proof-record.json

The first command installs the pinned toolchain, the second re-runs the solver and must print 0 errors, and the third confirms the file is the one the record describes. The mutation and replay gates run from two small scripts meant to be published with the folders.
