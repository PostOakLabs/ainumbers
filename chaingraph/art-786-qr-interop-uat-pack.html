QR Interop UAT Pack

A national QR scheme going live must test every issuer, acquirer and wallet against every other. This node turns a declared participant list and a scheme profile into a user-acceptance test pack: an interoperability matrix of ordered presenter/payer pairs, positive and negative cases drawn from the pinned field rules, reversal, refund and dispute cases, payee-name outcome cases, and per-phase exit criteria: domestic interoperability first, then the cross-border linkage phase. Every number on this page is recomputable from the run section below.

Presenter mode shows one step per screen. Arrow keys move, A toggles autoplay, Esc exits.
1
Step 1

Roles become ordered pairs

The pack starts from participants, not people: pseudonymous codes with roles from issuer, acquirer, wallet and aggregator. A payer side needs an account it can debit from; a presenter side needs acquiring capability.

The matrix covers every ordered (presenter, payer) pair whose roles can transact, so N×(N−1) at most. Self-pairs are never testable and impossible role pairs (an acquirer-only payer, an aggregator with neither seat) are excluded and counted with a reason, so the count always reconciles: matrix pairs plus role-excluded pairs equals N×(N−1), and self-pairs add N more exclusions. The same inputs always produce the same pack: case ids are derived from case content, not from a counter.

2
Step 2

Negative cases never carry live payloads

Every transactable pair gets positive static and dynamic cases, then negative cases described as mutations of a payload: the pack names what to break, it never emits a QR string carrying a merchant name.

The mutation set is fixed by the pinned field rules: bad CRC and the excluded-6304 generator bug, wrong currency against the profile's pinned ISO 4217 code, a payload missing its mandatory merchant account template, a malformed tag 62 additional-data template, and (where the profile forbids it, as the BR Code rules do for static payloads) a static payload carrying an amount. Each negative case names its rule reference and the pinned source section behind it. Participant codes, merchant names and account data never appear in any emitted case.

3
Step 3

Domestic first, then the cross-border phase

ASEAN cross-border QR links went bilateral pilot, then commercial, then expansion. The pack follows that order: the domestic matrix is phase one, and a cross-border phase exists only when foreign link profiles are declared.

Each phase carries exit criteria: all mandatory cases passed and no open severity-1 defect before the next phase begins. The domestic exit gate exists because a cross-border pilot on top of a broken domestic matrix wastes every participant's certification effort, the failure mode the bilateral-link rollouts hit. Optional toggles add full reversal, partial refund and dispute-lifecycle cases, and payee-name outcome cases over the match / close match / no match / not possible outcome set, to every domestic pair.

The three participants are fixed synthetic codes P1 (issuer + wallet), P2 (acquirer) and P3 (wallet), so the reconciliation is checkable by hand: six ordered pairs, the two with P2 as payer excluded as role-impossible, four matrix pairs, plus the three self-pair exclusions. Turning on cross-border adds one pair per acquiring-capable presenter against the linked foreign scheme. Toggling a category changes only which cases exist, never the matrix and never an id.
