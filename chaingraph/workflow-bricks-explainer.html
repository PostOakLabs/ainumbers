A ChainGraph workflow built brick by brick

A chain is a named, ordered list of catalog tools. This page follows x402-spend-evidence, a three-step chain in the Graph Index, while it runs: each step cites the hash of the step before it, and the run folds into one composite hash that outside authorities can timestamp and anyone can replay. Drag the scene to turn it.

Presenter mode shows one step per screen. Arrow keys move, A toggles autoplay, Esc exits.
The chain's steps are read from chaingraph.json in the public repository, and every hash on this page is quoted from the Agent Staircase explainer's live run of 26 September 2026 (UTC) against the public surfaces, with synthetic inputs. The scene draws recorded values and makes no network call.

Step 1 · The scene

One chain drawn as bricks

The scene animates one run of the x402-spend-evidence chain. An MCP host calls run_chain, three tool towers build in order, each tower passes the hash of the step before it, and the run folds into one composite hash that is anchored. Drag the scene to turn it.

The Graph Index lists 374 named chains and this page follows one of them. Double-click a building to open its page.

Step 3 · The link

Each step cites the hash of the step before it

run_chain threads each step's execution hash into the next step's parent_hashes and returns one composite hash over the steps that ran. Each step reads its own inputs from the caller or from the workflow's fixture, so only the hash link crosses between steps.

The first step is the root of the chain, so its parent_hashes list is empty. Step 2 cites step 1's hash and step 3 cites step 2's hash.

The scene's Tamper control edits step 2's input. The recomputed hash then no longer equals the hash step 3 cites, the link breaks, and the composite no longer verifies. The view is illustrative: the scene replays recorded values rather than calling the server.

Step 4 · The ledger

The composite and the ledger link

The run returns one composite execution hash plus a ledger_url. The link carries the run in the URL fragment and opens the Agent Work Ledger, which replays every step and verifies the execution hash in the browser.

A reader does not have to trust the server. Anyone holding the inputs can recompute a step's hash and compare it with the hash the receipt cites, and verify_execution_hash on the MCP server does that recomputation for any caller.

The ledger URL has the shape https://ledger.ainumbers.co/#a=v1.<encoded>, so the encoded artifact rides in the fragment and the URL is the only thing an agent has to pass on.

Step 5 · The anchors

Outside authorities timestamp the root

The session receipt's root went to three independent RFC 3161 timestamp authorities. Sigstore TSA, DigiCert and FreeTSA each signed it, within one second of each other.

The root is a Merkle root over the run's hashes, so each authority signed a root hash alone. The timestamps prove the root existed at a recorded time.

Step 6 · The check

Check it yourself

Every claim on this page can be re-derived from the public repository and the public surfaces.

  • Read the chain's step list in the Graph Index: the x402-spend-evidence entry in chaingraph.json names its three tools in order.
  • Compare the hashes with the Agent Staircase explainer, whose live-run answer quotes each step's hash and verdict plus the composite.
  • Copy an MCP call from the chain's page and send it to run_chain on mcp.ainumbers.co to run the chain and read the composite and the ledger link it returns.
  • Verify a step's hash with verify_execution_hash on the MCP server, passing the returned hash as claimed_hash.
  • Open a returned ledger_url and watch the ledger re-check each step in the browser.
