How WebMCP Macros runs one workflow

This estate publishes workflows whose steps are calculators on their own pages. WebMCP Macros, an independent open source Chrome extension by André Cipriani Bandarra (Apache-2.0), runs such a workflow as a small JSON program: the first page anchors a document hash and a claimed timestamp, the second page verifies that attestation, and a variable carries the first result to the second call. This page is written for a reader who has seen a form run in a browser and wants to see a workflow run end to end with no server and no model in the loop. It shows the two registrations, the program block by block with what each block reads and writes, the hop the program makes between the two pages, and a share string a reader can paste into the extension.

Presenter mode shows one step per screen. Arrow keys move, A toggles autoplay, Esc exits.
Same inputs give the same outputs. The program is plain JSON, the tools compute locally on their own pages, and the share string carries a checksum, so a reader can see exactly what a pasted macro will do before running it.
Part one · The workflow, the program and the hop

Two pages and one small program

What each page registers, what each block of the program reads and writes, and how execution moves from the first page to the second.

Step 1 · The workflow

The workflow and its two pages

The published workflow document-integrity-anchor has two steps. Step 1 runs on a page that anchors a document hash and a claimed timestamp into an electronic timestamp artifact. Step 2 runs on another page that verifies such an artifact: it re-checks the hash, the timestamp consistency and the algorithm, and reports four booleans. Each step's page registers its tool with the browser, and each registration declares an outputSchema naming exactly what the tool writes.

PageRegistered toolReads (inputSchema)Writes (outputSchema)
art-121-document-integrity-anchor.htmlanchor_document_integritydocument_hash, claimed_timestamp, document_type, hash_algorithmanchored, document_hash, document_type, timestamp_claim
art-122-timestamp-attestation-verifier.htmlverify_timestamp_attestationdocument_hash, presented_anchor, presented_timestamp, expected_algorithmverified, hash_match, ts_consistent, algo_match

Both registrations share one shape: a name, a description, a title, the input schema, the output schema, a read-only hint, and an execute function that fills the page's own form and runs the page's own compute. The declared outputSchema is what the macro editor reads to offer the fields of a saved result, which is why this workflow demonstrates the handoff cleanly: the fields of step 1's result are named before step 2 is ever written.

Step 3 · The hop

How the program moves between pages

Each of the two tools lives on its own document, so the program has to move. It does: an onSite block hands execution to the named site, and the extension's tab router finds that site's page. The run itself lives in the extension's background service worker, one run per starting tab, so the run survives the move.

Concretely: each site in the macro names its page with a URL match list and an optional startUrl. When the program enters onSite verifier, the router first looks for an open tab whose URL matches, then opens a new tab at the declared startUrl. The second call waits for the fresh page to report its tools before it runs, so a slow load delays the step instead of failing it, and a page that never reports fails the run with a message that says so. The router opens only the pages the sites declare, and only http or https, so a shared macro cannot steer the browser anywhere else.

Step 4 · The plain part

Why no model is needed here

Nothing in the run asks a model anything. The program is data, the runner interprets it, and the two tools compute. Each stage of the run is a plain lookup or a pure function:

  1. The trigger is a list lookup: the extension offers the macro when a page's tool list contains the named tool from the macro's trigger set.
  2. Every argument names its source: a typed input, a literal, or a get path into a saved result. The values in step 2's call all come from step 1's declared output.
  3. The hop names its destination: a URL match list and, when no tab matches, the site's declared startUrl. The router opens only http or https pages the sites declare.
  4. The verdicts are computed: each page runs its own kernel over its declared inputs, and the verifier reports the four booleans its outputSchema named.

Two more properties come from the format rather than the workflow. Every tool call and every loop iteration counts against a step limit (3000 by default), so a runaway shared program ends on its own. And a share string carries a checksum over its JSON: an altered string is refused, and a string from a newer format version is refused with a message rather than misread.

Determinism is the point: the kernels behind both pages are pure functions of their declared inputs, so the same paste runs the same steps and returns the same verdicts on every run.
