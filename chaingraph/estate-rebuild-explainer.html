One Merge Rebuilds the Whole Estate

Every count, catalog entry and sitemap line a reader or an agent sees is recomputed from source files. Nobody types those numbers and there is no database behind them: a merge to the source bricks is the only input, and one writer rebuilds everything derived from them. This page walks the assembly line, then follows one real change through it using hashes the estate itself publishes.

Goal of this animation

Show why a published count cannot drift from its source: readers never edit the derived pages, one writer recomputes them from the source files after every merge, and each step can be audited with real hashes from the estate.

Static page · delivered through Cloudflare's network · the site runs no database; every derived file is committed to the repository you can read.
Presenter mode shows one step per screen. Arrow keys move, A toggles autoplay, Esc exits.
1
Step 1

A PR changes source only

A change arrives as source bricks: a kernel, its node shard, a manifest and fixture vectors. The pull request never edits a derived file, because derived files have exactly one writer and a pull request is not it.

The rule that enforces this is the repository's single-writer rule: the regen workflow on main is the only process allowed to write catalog files, sitemaps, counts and receipt bundles. A pull request that regenerated them itself would be overwritten or rejected, so its author edits only the inputs.

2
Step 2

The merge queue assembles the whole tree and gates it

Before anything lands, the queue builds the derived tree in a throwaway directory and runs the blocking gates against that assembly, not against a half-updated checkout.

The throwaway assembly root means the gates see exactly what main would see after the merge: the regenerated catalog, sitemap and counts are all present, and validators copy-check the result before the queue lets the change through.

3
Step 3

After the merge one writer rebuilds the derived estate

Once the change is on main, the derived-artifacts regen workflow recomputes every derived class. Today that is 53 artifact classes: catalog, sitemaps, counts, hubs and one receipt bundle per freshly proven node. The published totals readers see, 702 live nodes and 762 live MCP tools, come out of that same pass.

4
Step 4

A line-ending guard rejects a bad tile

Not every brick deserves to land. One guard on the line inspects each file for stray carriage returns, the residue of a text file saved with the wrong line endings.

The guard is binary-aware: it tests whether a file is text before it complains, so a genuine binary tile sails through and a text file carrying carriage returns is kicked off the line. The rejected brick in this scene is the one to watch.

5
Step 5

The MCP worker refreshes its vendored copy

The MCP worker does not read the site repository at request time. It carries a vendored copy of the published tree and refreshes it from site main, so an agent calling the tool API sees the same bytes the site serves.

The refresh is itself a merge with the copied-from commit in its subject line. The refresh that carried this page's followed node named site main commit 423a86a6 and reported 2 stale files. When the vendor copy lags, a scheduled self-heal job opens the refresh automatically, so the gap never grows a direction nobody watches.

6
Step 6

Deploy runs only through gated pipelines, then a smoke step

Getting to main is not the finish. Deployment runs only through GitHub Actions pipelines that themselves run the gates, and after each deploy a smoke step calls the worker's tool endpoint to confirm it answers.

That closes the loop. Every published number is a pure function of the source bricks plus this pipeline, the pipeline is the only writer, and each hop leaves a hash a reader can recompute.
