Step 1

The verdict table and its pasted inputs

The caller pastes the decoded instruction list, the PaymentRequirements, the mint configuration and optional Ed25519 signature checks. Every clause answers three questions: what does the spec accept, what does the reference code accept, and where do they split.

Clauses: the amount rule, the single matching transfer, the destination associated token account, fee payer isolation, the net amount on a transfer-fee mint, the memo rule, transaction-version admission, and optional signature checks. The kernel reads nothing on-chain, calls no facilitator and looks up no balance; everything is recomputed from pasted bytes. Splits (extra.splits) are refused for this version rather than mis-judged, and inner (CPI) instructions are matched only when the caller pastes them, so a smart-wallet payment without its inner instructions reports zero matches instead of a verdict the bytes cannot support.

Step 2

The same overpayment passes one reader and fails the other

The spec outcome definition accepts any transfer of at least the required amount and tolerates overpayment. The static verification path rejects any amount that is not exactly equal.

Pinned at specs/schemes/exact/scheme_exact_svm.md in the x402 repo at the commit above: section 1.1 asks for a transfer of at least the required amount and section 1.4 says a matching transfer MAY exceed it and MUST NOT be less. The reference facilitator disagrees with itself in the other direction: the static path rejects any inequality (scheme.ts L1160), while the smart-wallet paths accept gross amounts greater or equal (smartWalletVerification.ts L657-662 and L727-781) and the balance-delta fallback accepts net deltas greater or equal (L795-803, L837-844). An underpaid transfer fails every reading; an exact amount passes every reading; an overpayment returns DIVERGES with both readings quoted.

Step 3

On a transfer-fee mint, the same payment nets less than it grosses

Token-2022 transfer fees are withheld at arrival. The static path compares the gross instruction amount; the balance-delta readers compare what actually landed. One payment can pass one and fail the other.

The withheld amount is min(ceil(gross times basis points over 10000), maximum_fee), the Token-2022 arithmetic this estate already ships in its transfer-fee reconciler, copied by hand. The spec text never mentions the transfer-fee extension by name; its balance-delta fallback (section 3.4, L446) compares a net quantity all the same. Two Kora advisories hit exactly this seam, GHSA-725g-w329-g7qr (transfer fee not deducted during payment verification) and GHSA-x442-m7cc-hr92 (unrecognized instruction stubs bypassing fee payer policy); both records carry severity medium and no patched version, and both are cited as facts, never rated.

Step 4

The recipient account depends on the token program

The associated token account derives from wallet, token program id and mint. Derive it under the classic Token program for a Token-2022 mint and you get a different, wrong, account.

The derivation is the pinned one this estate already audited as its own node: seeds [wallet, token program id, mint] under the associated-token program, with the canonical bump scan from 255 down to 1 and the off-curve rule. The kernel derives the account under the declared program and under the classic program side by side, so a transfer that pays the classic-program account of a Token-2022 mint is visible as wrong_program_ata rather than a mystery zero-match.

Step 5

The fee payer is a signature for fees only

The sponsor's fee payer must appear in no instruction account, no authority, no source. And since the June rewrite, the spec itself defines which transaction versions a charge may carry, so the version clause returns pass or fail instead of undefined.

The isolation rule is spec section 2.1.1: the fee payer signs for transaction fees and nothing else, with one bounded exception, it may be the recipient when it equals pay_to. The reference static path checks the narrower fact that its own signers are not the transfer authority, which is why the kernel implements the spec rule account by account and reports the difference as a fact. On versions: the spec now normatively defines transactionVersions (JSON integers 0 and 1, default 0, fail closed on anything else) and the reference reads the wire version before signature work, so spec and code agree here; the earlier stance, that version 1 was spec-undefined, is retired and recorded in the fixture notes.
