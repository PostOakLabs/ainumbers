Open designs: what has not been built yet

The AINumbers estate ships verifier tools, an artifact standard and a live receipt ledger, and a short list of ideas has stayed deliberately unbuilt because each one needs a ruling the estate has not made. This page publishes those six ideas as plain blueprints so a future row here, or a developer outside the project, can pick one up without access to any private planning surface. Every entry carries the same parts: a status line reading design (not built); the interfaces and data shapes it would use; what it reads from and emits into the estate, with each item tagged as either something the estate does today or a design; the constraints that bind it; the open source libraries it names with licence and review status; the open questions; and the ruling the estate would need first. Nothing on this page runs: there is no server, no coordinator and no signing key anywhere in these blueprints, and every page on this site makes zero network calls after load.

Design 1 · Ordering

An ordering log that takes one object at a timedesign (not built)

A small append-only log that gives a stable order to hash values for objects that have no other order. Each object id gets its own log, the log stores hashes only, and the running head of the log is a hash like any other hash, so the estate's existing timestamp path can anchor it.

Interfaces and data shapes

Interface sketchdesign
append(object_id, entry_hash) -> {seq, prev_hash, head_hash}

entry  = {seq, prev_hash, entry_hash}
head   = SHA-256 over the JCS canonical form of the last entry

What it reads and emits

  • The estate orders linked artifacts today through parent_hashesthe estate does this today, specified in the OpenChainGraph standard's chain execution section. A parent link orders artifacts that cite each other; the log idea exists for artifacts with no parent link between themdesign.
  • A log head is an ordinary SHA-256 hash, so it could be stamped through the same path as any other hash todaythe estate does this today: the timestamp service at anchor.ainumbers.co anchors hashes and the C2SP log verifier tool checks the result. Anchoring a log head periodically would need no new verifierdesign.
  • The log itself, its storage and its API, do not exist anywhere in the estatedesign. No AINumbers service runs an ordering log today.

Constraints

The log holds hashes only: no content, no names, no network identifiers, and no request logging. Any hosted component in this design is presented as something a reader could run, never as an AINumbers service. The JCS canonicalization behind the head hash stays exactly the shared canonicalizer the kernels use; the design builds no second one. One verifier per format holds here because the head needs no new verifier at all.

Open source libraries, licence and review status

None required for the page-level design. A real deployment would lean on its hosting platform's durable storage primitive; the design names no vendor and needs no cryptography library, because it reuses the estate's existing canonicalizer and timestamp path.

Open questions

  • Retention: how long a log keeps entries, and what the standard's anchor profile says about expired heads.
  • Whether parent_hashes already covers every ordering need, which would remove the reason for the log entirely.
  • Who operates such a log if it is ever built.

The ruling the estate needs first

A privacy ruling. An ordering party is a server the estate would run, and the estate today runs no service that holds user-derived data, so building this means amending that promise first, plus a review of the deployment binding and the contract's deployment rules.

In the AINumbers estate. The order-without-a-clock walkthrough shows why ordering and timestamping are different problems, and the chain execution section of the standard is where parent_hashes ordering lives today. See order without a clock and the OpenChainGraph standard.

Design 2 · Randomness

A randomness coordinator for joint commitsdesign (not built)

When several parties want one random value that none of them can bias, each commits to a secret, all commitments are collected, then all secrets are revealed and combined. A relay can carry those messages while never learning any secret. The estate needs no such relay today, so this stays a blueprint.

Interfaces and data shapes

Message formatsdesign
commit = SHA-256(salt || secret)
reveal = {salt, secret}
joint  = SHA-256(sorted reveals)

relay states: collect -> close -> reveal, or abort

The state machine must state its failure mode plainly: the last party to reveal can see every other reveal before publishing its own, and can abort if it dislikes the joint value. That last-revealer bias is a property of the design, written on the blueprint in plain sight.

What it reads and emits

  • Salted SHA-256 commitments are a scheme the standard already specifies, so the commit and reveal message shapes reuse an existing, specified constructionthe estate does this today.
  • The estate uses an external public randomness beacon today: two fair-sampling computations take a drand quicknet pulse as declared inputthe estate does this today, and a coordinator design could accept such a pulse as an external bias-breaking value instead of running its own reveal phasedesign.
  • A coordinator relay does not exist anywhere in the estate. No AINumbers service collects commitments or runs a randomness ceremonydesign.

Constraints

The relay holds commitments only, keeps no accounts, and keeps state only until the ceremony closes or expires. The privacy promise from the ordering entry applies identically: a coordinator is a server somebody runs, shown as a design a reader could deploy, never as an AINumbers service. Pages on this site make zero network calls, so no page could host a live ceremony even if the design existed.

Open source libraries, licence and review status

The measured candidate for any offline verification of beacon values is @noble/curves 2.4.0 and @noble/hashes 2.4.0 (MIT licence; the curves library had an independent security review of its 2.3.0 release published in August 2026). A 2026-10-22 measurement verified a drand quicknet round offline with these libraries alone, from their published tarballs, with no beacon client. No code from them is embedded on this page.

Open questions

  • Bias on abort: what the remaining parties do when the last revealer walks away.
  • Whether the estate ever needs a multi-party salt, which the existing ceremony walkthrough declines to claim either way.

The ruling the estate needs first

The same privacy ruling as the ordering log, plus a plainer one: a decision that there is no need today. Until a real use appears, the right label is the one this page carries.

In the AINumbers estate. The randomness ceremony walkthrough shows the relay seeing commitments only, and the randomness demo shows a joint value built from commitments and reveals with no server at all. Beacon use today lives in the two fair-sampling computations. See the randomness ceremony walkthrough, the one-honest-party randomness demo, art-583 and art-774.

Design 3 · Keys

Distributed key generation and threshold signingdesign (not built)

A threshold key sits in several hands at once: a quorum of holders produces one ordinary Schnorr signature under one public key, and no single holder ever holds the whole key. The blueprint is the round list a developer would run and the test vectors they would check against rather than a running signer.

Interfaces and data shapes

Round listdesign
Key generation, three rounds, per @noble/curves
  (the Zcash Foundation construction; never called an RFC):
  DKG.round1 -> DKG.round2 -> DKG.round3  -> group public key

Signing, per RFC 9591 FROST:
  commit -> sign -> aggregate  -> one ordinary Schnorr signature

Excluded: MuSig2 (no independent security review of the
  implementation the estate would vendor).

Wording matters here and the blueprint pins it: the three-round key generation follows a library's implementation of the Zcash Foundation construction and is never called an RFC, while the signing rounds are the RFC 9591 FROST rounds.

What it reads and emits

  • The estate's receipt verifiers check ordinary single-signer signatures todaythe estate does this today, which is exactly why a threshold signature would verify with no verifier change: to any outside checker it is one signature under one keydesign.
  • Estate receipts are signed by single keys. No estate receipt is threshold-signed, and no threshold signer exists anywhere in the estatedesign.
  • The threshold-signing walkthrough on this site already carries a recorded 2-of-3 transcript, generated offline before the page was written, that a developer could use as test input for their own implementationthe estate does this today.

Constraints

No hand-rolled cryptography: any implementation would vendor a reviewed library, pinned to an exact release, never an in-page reimplementation. The estate's canonicalization and hash preimage rules are untouched by this design, because threshold signing replaces nothing in the artifact format. The recorded transcript on the walkthrough page exists precisely so nobody has to hand-type values that look real.

Open source libraries, licence and review status

@noble/curves 2.4.0 (MIT; independent security review of v2.3.0 published August 2026) implements the three-round distributed key generation and RFC 9591 FROST signing. The Zcash Foundation's Rust FROST implementation (MIT or Apache 2.0) had an independent review of its v0.6.0 release. Both are references for a developer, and neither is embedded on this page.

Open questions

  • Which devices would hold shares, and how a quorum is chosen across them.
  • Whether a browser-side bundle of the library is needed, which a 2026-10-22 measurement answered narrowly: the library ships no single-file browser build, so one would be built at page-build time from a pinned tarball.

The ruling the estate needs first

A decision that is already answerable today: the estate does not want threshold-signed receipts now, so nothing blocks an outside developer from building one, and the estate would only revisit this if it wanted its own receipts carried by a quorum.

In the AINumbers estate. The threshold walkthrough records a full 2-of-3 ceremony with a distributed-key-generation track, and the receipt verifier shows the single-signer checks a threshold signature would sail through. See the threshold signing walkthrough and the OCG receipt verifier.

Design 4 · Elision formats

Gordian Envelope in library modedesign (not built)

Gordian Envelope is a published format for structured, elidable commitments: a tree of predicates whose parts can be hidden while the commitment to the whole survives. The estate's pages teach the idea with its own WebCrypto tree, and this blueprint is what a conformant implementation using the real Envelope library would need.

Interfaces and data shapes

What a conformant implementation needsdesign
dCBOR-encoded bytes          deterministic CBOR rather than JSON
tree digest                  determined envelope digest over the tree
elision                      suppress parts, digest of the root unchanged
signature                    over the root digest, carried in the tree
interop check                upstream published test vectors must pass

What it reads and emits

  • The estate's own pages teach elision with a teaching tree that reuses the estate's canonicalization, and the comparison workbench shows what hiding a field does to a commitmentthe estate does this today.
  • The estate does not emit or consume Gordian Envelope bytes anywhere. Its artifact hashes use the JCS-based execution_hash, and exporting an execution_hash as an Envelope is explicitly dropped from this design, because dCBOR and JCS are different canonicalizationsdesign. The estate's teaching tree is not interoperable with real Envelope implementations, and the pages say so on the page.

Constraints

The licence handling is the measured obstacle: the library's licence requires the full notice text to travel with the source, so any page embedding it must carry the complete licence text inline and keep a bundler from stripping it. The estate has no precedent page for that, which is part of why this stays a blueprint. Public attribution only: the format is documented publicly as the draft-mcnally-envelope Internet draft and in Blockchain Commons documentation, and the reference implementation is beta software.

Open source libraries, licence and review status

@blockchaincommons/envelope 1.0.0-beta.5 and @blockchaincommons/dcbor 1.0.0-beta.5 (BSD-2-Clause-Patent; beta, no independent security review). A 2026-10-22 measurement confirmed both ship browser-safe ES modules, with a dependency closure measured at roughly 243 KB for the envelope package before tree-shaking. No code from either is embedded on this page.

Open questions

  • Whether any estate surface ever needs interoperable Envelope output at all, given the JCS-based artifact hash.
  • How an inline licence notice survives minification in the estate's single-file page discipline.

The ruling the estate needs first

A licensing ruling: whether the estate will carry a full third-party licence text inline on a public page at all. Every earlier page kept third-party code out rather than answer it.

In the AINumbers estate. The elision comparison workbench hides fields from a live commitment and shows what survives, the prove-without-revealing ideas appear in the walkthroughs, and the SD-JWT workbench shows the disclosure-list pattern the standard itself adopted for selective disclosure. See the elision comparison workbench and the SD-JWT disclosure workbench.

Design 5 · Authority

Principal-authority fields in the Policy Mandatedesign (not built)

When an agent acts for a principal, who approved it, within what scope, and who can revoke it. The estate's Policy Mandate carries scope and caveats today, and this blueprint proposes the three optional members a delegation story would add. The field names are proposed and absent from the schema, and nothing on this page validates against them.

Interfaces and data shapes

Draft fragment (proposed, absent from the schema)design
delegation_chain: [
  {principal_ref, delegate_ref, scope_hash, expires, signature}
]
human_checkpoints: [
  {trigger, device_class}
]
revocable_by: [principal_ref]

All three would be optional members. Version 1.0 of the mandate stays byte-identical, exports that predate the members keep validating, and the retained legacy identifiers in the tools are untouched. This mirrors how the estate added its one post-1.0 member so far: one optional top-level member, everything else unchanged.

What it reads and emits

  • The Policy Mandate today carries scope, obligations and, since v1.1, one optional caveats memberthe estate does this today.
  • The standard's work mandates section already models delegated work with mandate documents and mandate hashesthe estate does this today, and any delegation-fields amendment should be checked against it first, because some of this design may belong there rather than in the Policy Mandatedesign.
  • No delegation chain, human checkpoint or revocation field exists in any published estate schema todaydesign.

Constraints

Optional members only; legacy exports must keep validating unchanged; the signature scheme per delegation hop is deliberately unpicked in the fragment, because choosing one is exactly the kind of decision an amendment process exists for. Revocation raises the hardest open question: distributing a revocation with no server is unsolved in this fragment and stated as unsolved.

Open source libraries, licence and review status

Reference formats for capability delegation exist, notably UCAN and Biscuit (Biscuit is Apache 2.0 with a WASM build), but neither has been vetted for the estate's constraints, so the blueprint names them as reading rather than as dependencies. Nothing is embedded on this page.

Open questions

  • Signature scheme per hop, and whether the scope hash reuses the estate's canonicalizer.
  • Revocation distribution without a server.
  • Overlap with the standard's work mandates: extend or reuse.

The ruling the estate needs first

A contract amendment. The Policy Mandate schema is defined in the estate's build contract, so the first step is an amendment number, a placement check, and only then any code.

In the AINumbers estate. The agent-authority walkthrough renders a decision lineage and labels spec-pending fields as exactly that, and the tools already export Policy Mandates that validate against the published schema. See the agent-principal authority walkthrough.

Design 6 · Data

A signing and recovery holder datasetdesign (not built)

Choosing who holds key shares is a design exercise in spread: by region, by authentication type, by person or organisation, by role in the quorum. A dataset of holder properties would let developers reason about that spread with real rows. This entry is a schema and a discipline rather than a tool, and it is deliberately the least built-out idea on the page.

Interfaces and data shapes

Dataset schemadesign
{holder_class, region, auth_type, person_or_org,
 k_of_n_role, source_url, checked_on}

rules: no vendor ranking; no negative claim without
  a citation; every row carries its source and a
  checked-on date; stale rows are refreshed or dropped

What it reads and emits

  • The threshold walkthrough's holder-choice step shows the property axes, with properties only and no vendors namedthe estate does this today.
  • No holder dataset exists anywhere in the estate, published or internaldesign. Building one is data work with a maintenance obligation, which is why it is a blueprint rather than a page.

Constraints

The defamation and staleness risks set the rules: no ranking of vendors, no negative claim without a citation, every row dated and sourced, and a named refresh owner before any build. Outside developers are the natural owners of such a dataset, which is why this blueprint describes it so a third party could run with it.

Open source libraries, licence and review status

None. This entry is a data schema and an editorial discipline; it needs no library, and no code is embedded on this page.

Open questions

  • Who sources the rows and who refreshes them, before anything is built.
  • What granularity serves a quorum design without becoming a vendor directory.

The ruling the estate needs first

A sourcing and refresh ruling: a named owner for the data and its update cadence, agreed before the first row exists.

In the AINumbers estate. The holder-choice step of the threshold walkthrough is where these property axes appear today. See the threshold signing walkthrough.
