Control Test Exception Disposition Check

Note (dated 2026-08-04): a chain composes independent computations performed in an analytical order. No step's output is carried into the next step by the execution model; each step computes from its own declared inputs. This is true of every chain on this site, including chains whose per-step copy below reads as a data handoff.

Four-stage check for a control test: plan an attribute sample, reconcile a control test into a conclusion with exceptions, assemble a signed workpaper bundle that records a disposition for each exception, and close with a session receipt over the run execution hashes. Each stage is an independent run from its own declared inputs.

SOX 404 / ICFR Sampling · Control Test · Workpaper Bundle PCAOB AS 1215 3 compute steps + receipt
Chain summary
A sampling plan alone tests nothing, a test conclusion alone leaves exceptions undisposed, and a bundle alone has no test behind it. This chain runs those three questions in order, as independent runs: a sample plan over declared policy inputs and a declared population hash, a control test reconciliation over a declared sample and declared per-item results, and a workpaper bundle over a declared procedure id, population hash, kernel artifacts and exception dispositions. Nodes: ART-458 → ART-461 → ART-465 → CRY-05.
gold border = terminal receipt stage
Stage 1: Attribute Sampling Plan
1
plan_attribute_sample · ART-458
Plan an attribute sample from caller-declared confidence level, tolerable deviation rate, expected deviation rate, population size and population hash, using the standard zero-expected-deviation Poisson formula with an expansion factor for a nonzero expected deviation rate. Item selection is deterministic interval sampling over the caller-declared population hash, so any auditor can replay the same sample from the same declared inputs. If the tolerable deviation rate is at or below the expected deviation rate, the plan reframes to a full-population census and flags SAMPLE_PLAN_INDEFENSIBLE_FULL_CENSUS. This stage selects items only. It tests nothing.

Stage 2: Control Test Evidence
2
compose_control_test_evidence · ART-461
Reconcile a caller-declared sample and per-item test results into a test conclusion, exception count and exception items for a declared control and reporting period. The tester is recorded under the SOX 404 / PCAOB AS 1215 preparer role, and every test carries a fixed review_required gate for reviewer sign-off. An exception count above zero flags a deficiency candidate only, with classification_pending true and reason_code null. Severity classification is a separate human reviewer approval record. This stage reconciles declared facts only. It judges no severity and no materiality.

Stage 3: Workpaper Bundle
3
compose_workpaper_bundle · ART-465
Assemble a workpaper bundle from a caller-declared procedure id, population hash, kernel artifacts and exception dispositions, with preparer, reviewer and partner sign-off roles. Exceptions are grouped by control, and a disposition is required per group and per item. A bundle with every exception dispositioned carries the flag WORKPAPER_BUNDLE_ALL_EXCEPTIONS_DISPOSED. A bundle with any exception lacking a disposition refuses with WORKPAPER_BUNDLE_UNDISPOSED_EXCEPTION. Partner release is recorded with gate_status review_required. This stage records dispositions. It judges no disposition as correct, and it aggregates no severity.

Full Chain MCP Sequence

Run the four tools in order. Each run uses its own declared inputs. The step 2 run declares the same population hash and the sample items from the step 1 run. The step 3 run declares the same population hash and the step 1 and step 2 execution hashes as kernel artifacts. No run reads another run output directly; the user supplies the cited values again as declared inputs.

Full chain: 4 MCP calls

Scope

Scope: workpaper completeness for a SOX 404 / ICFR control test, using attribute sampling under the standard zero-expected-deviation Poisson formula, a deterministic interval sample over a caller-declared population hash, a test reconciliation against a caller-set tolerable exception count, and a signed bundle with preparer, reviewer and partner roles. The worked example uses a management-review control, because precision documentation for management review controls is a current PCAOB inspection focus, along with complementary user entity controls, walkthrough documentation, control performance documentation, and AI-driven controls governance. The bundle sign-off roles map to those inspection expectations: preparer records the test record, reviewer records the group and item dispositions and the severity aggregation judgement, partner records the release under gate_status review_required.

Out of scope

Out of scope: a severity verdict; an audit opinion; a re-run of upstream kernels; a recomputed population hash; a judgement that any disposition is correct; a countersignature enforcement; a sample drawn from a live population extract.

What the bundle records, stated plainly

Art-465 records that a disposition was declared for each exception. It does not judge whether a disposition was correct. A bundle with every exception dispositioned is a record of dispositions. A reviewer still judges correctness, and a reviewer still judges severity. Exceptions are grouped by control, and a disposition is required per group and per item: in the worked example the single group is control MRC-01, and its group disposition is recorded through the item disposition for item-002, remediate_and_retest, with reason_code REVIEWER_FOLLOW_UP_REQUIRED. Aggregation for severity is a human reviewer judgement recorded in the bundle. It is computed by no kernel in this chain: art-461 flags a deficiency candidate only, with classification_pending true and reason_code null, and art-465 checks only that a disposition was declared.

Population hash: carried, and checked by hand

Population hash is carried between steps as a declared field. It is carried, and it is not cross-verified. No kernel in this chain verifies that the sample tested in step 2 is the sample planned in step 1, or that the exceptions bundled in step 3 are the exceptions found in step 2. A bundle whose population hash matches only because the user copied it proves a carried field, and it proves nothing else about the sample. The manual check is the control: the reviewer compares the step 1 selected_indices, the step 2 sample, and the step 3 exceptions, item by item, before relying on the bundle. The chain is described as a sequence of independent runs with a manual comparison step. It is described as end-to-end verified in no place on this page.

Art-465 acceptance, quoted

Acceptance basis, quoted from the art-465 node shard description: the bundle takes "the prior substantive-recalculation kernels' execution-hash artifacts (art-462 JE rule screen, art-463 recalc suite, art-464 confirmation matcher, or any other procedure kernel)". Art-461 is used here as that other procedure kernel. The art-465 kernel comment uses the wording "any other substantive-procedure kernel". The node shard description governs the node surface, and this package follows the shard wording, as approved. Art-460 is dropped from this chain: the shipped icfr-sampling-ipe-evidence-check chain ends at the test conclusion, while this chain adds the disposition step, so its terminal question is different.
