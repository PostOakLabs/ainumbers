Threat model: anchor relay

Scope: anchor.ainumbers.co, a Cloudflare Worker (src/worker.mjs, wrangler.jsonc in the Anchor Suite repository) that relays timestamp requests to public authorities and exposes a small MCP tool set. Written from that source on 5 November 2026. All threat models.

Assets

  • Timestamp proofs. A returned proof must be the authority's real reply, unmodified.
  • The hash a visitor submits. It is a digest, not the artifact, but it can still identify a document to anyone who already has the document.
  • Upstream goodwill. The relay spends the free quota of third-party authorities. Abuse would get the relay blocked.

Trust boundaries

  • Browser or agent to the Worker, over TLS. No authentication (authentication: none in the discovery document).
  • Worker to third-party timestamp authorities: FreeTSA, DigiCert, Sectigo, Sigstore, GitHub, four OpenTimestamps calendars and the Sigsum log. These operators receive the request and see the relay's address, not the visitor's.
  • Static pages (public/) are served by the platform without invoking the Worker. Only /relay/* and /mcp run code.

Adversaries

  • A1. A client that floods the relay to exhaust upstream quotas.
  • A2. A client that sends large or malformed bodies, or uses the relay as a general proxy.
  • A3. A hostile origin that calls the relay from a victim's browser.
  • A4. A hostile or faulty authority that returns a bad proof.

In scope and out of scope

In scope: relay abuse, request size, who may call from a browser, what the relay stores about a request, and the page headers on the anchor site.

Out of scope: the trustworthiness of each timestamp authority; the legal weight of a timestamp; availability of upstream services.

UNTESTABLE claims

  • "Stores nothing." The source has no write path, and that is what this page relies on. Cloudflare's own request logging for the Worker is not controlled from the code and is not tested here; see data handling.
  • What each authority retains. Third parties receive the hash and log it under their own terms. We cannot test or limit that.
  • That the headers are served. The header file is in the repository. We did not find a gate in the site repository that fetches the live anchor site and compares headers.
  • The 4-per-minute limit on the live service. It is configured in code, not probed.

Residual risk

  • A hash submitted for anchoring is disclosed to the chosen authorities, and some of them publish what they stamp (a Bitcoin-anchored calendar and a public transparency log are permanent). Submit a digest only if you are content for that digest to be public forever.
  • A client behind shared infrastructure shares the per-IP limit, and an attacker with many addresses can still consume upstream quota.
  • The relay is a single point of failure for in-browser anchoring; verification of an existing proof does not need it.
